# План доработки: задание 9 «Многопоточная асинхронная обработка команд»

**Цель.** Перевести обработку команд из синхронной (всё выполняется в потоке вызывающего `receive()`) в асинхронную: при старте программы создаются три дополнительных потока — `log` (вывод в консоль), `file1` и `file2` (вывод в файлы), блок команд после формирования отправляется в консоль и сразу в файл через очереди.

**Жёсткое ограничение.** Внешний интерфейс `libasync/include/async/async.h` (`connect`, `receive`, `disconnect`) не меняется — меняется только внутренняя реализация. Формат консольного вывода (`bulk: a, b, c`) и логика парсинга (коллекторы, группировка блоков) остаются как в задании 7.

**Файлы, которых коснётся переделка.** `libasync/src/async.cpp`, `libasync/include/parser.h` (+ `src/parser.cpp`), `libasync/include/processor/printer.h`, `libasync/include/processor/saver.h`, `libasync/src/scheduler.cpp`, `libasync/CMakeLists.txt`, тесты `libasync/tests/test_async_mt.cpp`. Новые файлы: очередь и диспетчер (см. ниже).

---

## 1. Диспетчер и воркер-потоки (log, file1, file2)

1. **Создать класс `Dispatcher`** — синглтон, аналогичный `Scheduler` (функция-локальный статик `Dispatcher &shared() noexcept`):
   - новые файлы: `libasync/include/dispatcher.h`, `libasync/src/dispatcher.cpp`;
   - владеет тремя потоками (`std::thread`): `log_thread_`, `file_thread_1_`, `file_thread_2_` и двумя очередями (см. пункт 2);
   - методы: `void start()`, `void dispatch(const Collector::Bulk &)`, `void unregister_context()` (или `stop()`/`shutdown()`), внутренние `worker_loop_log()`, `worker_loop_file()`.
2. **Старт потоков — лениво, при первом вызове `connect()`** («при старте программы» для внешнего кода):
   - в `Scheduler::start_task()` (или в `async.cpp::connect()`) добавить вызов `Dispatcher::shared().start()`, который создаёт три потока ровно один раз (флаг `started_` под мьютексом);
   - lazy-инициализация безопаснее статического объекта для shared-библиотеки (нет проблем порядка статической инициализации).
3. **Завершение потоков — когда закрыт последний контекст**:
   - диспетчер ведёт счётчик активных контекстов: `start_task()` инкрементирует, `stop_task()` декрементирует;
   - при достижении нуля: установить флаг `stopped_`, уведомить условные переменные, дождаться `join()` всех трёх потоков;
   - порядок важен: сначала `parser->stop()` (flush последнего блока), потом завершение потоков, иначе вывод потеряется;
   - следующий `connect()` снова запускает потоки (рестарт).
4. **Логика воркер-цикла** (одинакова для всех трёх потоков): `pop()` из своей очереди (блокирующий, с обработкой spurious wakeup и флага остановки) → обработка → повтор; по флагу остановки — выход из цикла.
5. **Обработка исключений в потоках:** `Saver::process()` сейчас бросает `std::runtime_error` (не открылся файл), а интерфейс `Processor::process` — `noexcept`. В воркер-цикле обернуть обработку в `try/catch` (вывод ошибки в `stderr`), чтобы поток не завершался через `std::terminate()`.
6. **CMake:** добавить `"src/dispatcher.cpp"` (и при необходимости `"include/queue.h"`) в `add_library(async SHARED ...)` в `libasync/CMakeLists.txt`.
7. **Имена потоков** (опционально, для отладки): задать `pthread_setname_np` / `std::thread` name — «log», «file1», «file2».

## 2. Очереди команд

1. **Создать потокобезопасную очередь `BlockingQueue<T>`** — новый файл `libasync/include/queue.h`:
   - поля: `std::mutex m_`, `std::condition_variable cv_`, `std::deque<T> q_`, `bool closed_`;
   - методы: `void push(const T &)` (или `push(T &&)`), `T pop()` (блокирующий; по `closed_` и пустой очереди — бросает исключение или возвращает признак окончания), опционально `bool try_pop(T &)` и `void close()`.
2. **Две очереди в `Dispatcher`** (тип элемента — `Collector::Bulk` из `libasync/include/collector/collector.h`):
   - `console_queue_` — обслуживает только поток `log`;
   - `file_queue_` — единая очередь, которую обслуживают **оба** файловых потока одновременно (это и есть рекомендованное заданием «лучшее решение»).
3. **Изменить `Parser::flush()`** (`libasync/src/parser.cpp`): вместо цикла
   `for (const auto &p : p_processors) p->process(bulk);`
   вызвать `Dispatcher::shared().dispatch(bulk)`, который делает `push` в `console_queue_` и `push` в `file_queue_` и сразу возвращается — `receive()` перестаёт блокировать на I/O (это и есть «асинхронность»).
4. **Убрать создание процессоров из `connect()`** (`libasync/src/async.cpp`): сейчас там `t.parser->add_processor(std::make_shared<Printer>())` и то же для `Saver` — эти строки удаляются, потому что `Printer`/`Saver` становятся собственностью воркеров диспетчера (по одному экземпляру на воркер). Вектор `p_processors` в `Parser` можно удалить вместе с `add_processor()`.
5. **Поток `log`:** `pop()` из `console_queue_` → `Printer::process(bulk)` → `std::cout`. FIFO-очередь сохраняет порядок блоков в рамках контекста (контекст всегда обслуживает один поток) — это требование проверки «вывод соответствует заданию 7».
6. **Потоки `file1`/`file2`:** оба делают `pop()` из одной `file_queue_` → каждый вызывает `Saver::process(bulk)` своего экземпляра. Порядок между файлами не важен — каждый блок пишется в отдельный файл.
7. **Мьютексы в `Printer` и `Saver`:** статический мьютекс в `Printer::process` больше не нужен (писатель один — поток `log`); мьютекс в `Saver::save_to_file` тоже (см. пункт 3.4).

## 3. Уникальные имена файлов

1. **Добавить постфикс в `Saver`** (`libasync/include/processor/saver.h`):
   - поле `std::string postfix_` и конструктор `explicit Saver(std::string postfix)`;
   - `make_filename`: `std::format("bulk{}_{}.log", static_cast<uint64_t>(t), postfix_)` — timestamp остаётся в имени, постфикс дописывается (требование задания: точности `time_t` не хватает, два блока за одну секунду не должны слиться в один файл).
2. **Выдать постфиксы при создании воркеров** в `Dispatcher::start()`:
   - поток `file1` получает постфикс `"1"`, поток `file2` — `"2"` (или `"f1"`/`"f2"`);
   - постфикс — стабильный счётчик, назначается один раз при старте и **гарантированно различается у файловых потоков**; не использовать `std::this_thread::get_id()` (значения могут повторно использоваться и нечитаемы в имени файла).
3. **Разместить экземпляры `Saver`:** `Dispatcher` хранит два `std::shared_ptr<Saver>` (или `unique_ptr`), по одному на файловый поток; каждый `Saver` вызывается строго из своего потока.
4. **Убрать мьютекс из `Saver::save_to_file`:** с уникальными постфиксами два потока физически не могут писать в один файл (имена различаются), а один `Saver` всегда вызывается одним потоком — синхронизация не нужна.
5. **DI-контейнер (опционально):** обновить `RealContainer::saver()` под сигнатуру с постфиксом, если решено выдавать `Saver` через контейнер, а не создавать в `Dispatcher` напрямую.

## 4. Демо main.cpp

1. **API не меняется — `src/main.cpp` в основном остаётся как есть:** `connect(n)`, цикл чтения строк из `stdin` с вызовами `receive(...)`, `disconnect(p)` — все три функции уже демонстрируются, что соответствует требованию «исполняемый файл с демонстрацией всех вызовов».
2. **Гарантировать дренаж очередей перед выходом:** с асинхронной обработкой вывод уходит в потоки, поэтому процесс не должен завершиться раньше, чем `log` и файловые потоки обработают очереди. Рабочий вариант — **семантика `disconnect()`**: он завершает текущий блок (flush) и дожидается, пока очереди опустеют (диспетчер ждёт `pop()` до пустой очереди / флага). Тогда `main.cpp` не требует изменений, а «вывод соответствует заданию 7» выполняется даже на больших объёмах без пауз.
3. **Проверить отсутствие deadlock** на выходе: `disconnect()` (последний контекст) → дренаж → `join()` потоков — программа должна завершаться штатно, без зависаний и потери вывода.
4. **Прогнать вручную:** `echo -e "cmd1\ncmd2\ncmd3" | ./bulk 3` и аналогичные сценарии из задания 7 (включая динамические блоки `{...}`) — сравнить консольный вывод с эталоном.

## 5. Верификация по заданию

1. **Сборка и тесты:** `cmake -S . -B .build` → `cmake --build .build` → `ctest --test-dir .build --output-on-failure`; то же для TSan-конфигурации (`.build-tsan`, `-DASYNC_TSAN=ON`); прогнать `./self_check.sh` (он покрывает обычную сборку, TSan и стабильность `--repeat until-fail:20`).
2. **Пакет:** `cmake --build .build --target package` — убедиться, что в DEB входят `libasync.so` (библиотека в пакете `async`) и исполняемый файл `bulk`; установить пакет (`dpkg -i` или `cmake --install` на staging-префикс) и проверить, что библиотека легла по стандартному пути (`/usr/local/lib` / `/usr/lib`) и заголовок `async/async.h` доступен.
3. **Внешний тестовый код (по разделу «Проверка» задания):** написать отдельный `main.cpp`-пример, который подключает `<async/async.h>` и линкуется с установленной библиотекой (`-lasync` с `-I`/`-L` на стандартные пути), и запустить его с тестовыми данными: **порциями, в разных контекстах, в большом объёме, без пауз**.
4. **Сверить вывод с заданием 7:** консоль — строки вида `bulk: a, b, c`, порядок в рамках каждого контекста сохраняется, никакие команды не потеряны/не задвоены; файлы — по одному на блок, имена `bulk{ts}_{postfix}.log`, оба файловых потока реально пишут файлы (встречаются оба постфикса).
5. **CI (опционально):** в `.github/workflows/release.yml` после шага `Package` добавить шаг установки пакета и smoke-запуск `bulk` с тестовыми данными — чтобы проверка «установка → линковка → запуск» выполнялась автоматически.

## 6. Тесты

1. **Расширить `libasync/tests/test_async_mt.cpp`** (инфраструктура `LineCapture` и фикстура `MtFixture` уже есть и переиспользуется):
   - **Асинхронная доставка:** после `connect` + серии `receive` + `disconnect` все ожидаемые bulk-строки появились в консоли (точное равенство по числу, составу и порядку в рамках контекста) — проверяет, что асинхронный путь ничего не теряет;
   - **Файлы:** после теста прочитать все `bulk*.log` из текущей директории (фикстура уже умеет их чистить), проверить количество файлов = количеству блоков и состав содержимого каждого файла;
   - **Уникальность имён:** два блока, сформированных в пределах одной секунды, должны лечь в **разные** файлы (постфикс сработал);
   - **Оба файловых потока работают:** на достаточно большом объёме блоков среди файлов встречаются оба постфикса (не делать это строгой проверкой на малых объёмах — распределение между потоками не детерминировано, можно проверить формат имени и уникальность, а распределение — как информационную проверку);
   - **Порядок в рамках контекста:** строки одного контекста в консоли идут в порядке отправки (FIFO-очередь + один поток на контекст).
2. **Детерминизм тестов:** полагаться на семантику «`disconnect()` ждёт дренажа» — тест завершается только когда весь вывод реально обработан, иначе возможны флаки («потерянный» хвост очереди при сравнении).
3. **ThreadSanitizer:** прогнать новые тесты в `.build-tsan` — ловит гонки в `BlockingQueue` (мьютекс/condvar) и в жизненном цикле `Dispatcher` (старт/стоп/рестарт потоков), включая стресс-тест `StressConnectReceiveDisconnectChurn` с параллельной сменой контекстов.
4. **Стабильность:** добавить новые тесты в прогон `self_check.sh` (повтор `--repeat until-fail:20`), чтобы отловить редкие гонки, которые не ловятся единичным запуском.
